# 开发变更记录：开放接口队列优先级调整为 API 优先

- **日期**: 2026-09-30

## 1. 变更摘要

将开放接口作业在 `cnki` 队列中的优先级由 `10`（低于网页任务）改为 `-1`（高于网页任务），
使 API 作业优先出队，不再被网页检索任务积压拖延。

单处改动：`app/routers/openapi_v1.py` 的 `API_QUEUE_PRIORITY`。

## 2. 为什么改

原设计（见 `20260929_开放接口元数据检索.md` 第 6.1 节）刻意让网页任务优先，理由是网页用户在看页面。
但实际使用中，agent 侧对「等待」更敏感：网页用户能直观看到排队位置，而 API 调用方只有轮询，
长时间排队容易被误判为卡死。

`dequeue` 排序为 `priority ASC, created_at ASC`，因此把 API 的 priority 调到比网页的 `0` 更小即可优先出队。

## 3. 澄清：网页 PDF 下载不影响 API 检索

变更讨论中确认了一个常见误解——网页的 PDF 下载**不会**占用 API 检索的队列槽位：

| 动作 | 队列 | 并发 | 入口 |
|------|------|------|------|
| 网页检索 | `cnki` | 1 | `app/routers/meta_tasks.py`、`app/routers/task_instances.py` |
| 网页下载 PDF | `download` | 1 | `app/routers/task_instances.py` |
| API 检索 | `cnki` | 1 | `app/routers/openapi_v1.py` |

`download` 与 `cnki` 是两条独立队列，由各自的 worker 消费（`app/main.py::_start_worker`、`worker_runner.py`），
`dequeue(queue_type)` 按队列过滤，二者互不可见。所以网页批量下载跑几小时，也不会让 API 检索多排一秒。

真正会与 API 争抢 `cnki` 槽位的只有**网页检索任务**，本次改动正是针对它。

## 4. 影响与副作用

- `queue_position` 语义同步更新：现在只有**同优先级的更早 API 作业**才排在前面（`_queue_position` 查询逻辑无需改动，`priority < API_QUEUE_PRIORITY` 自然恒为 0 行）；
- 副作用：多个 API 作业并存时会按提交顺序依次执行，网页检索任务排在其后。若 API 侧被滥用（大量并发提交），会明显延长网页用户的等待。当前未启用按 Key 限流，仍依赖调用方自律（建议同一 Key 同时最多 1 个在途作业）；
- 未拆分新队列、未新增第二个 CNKI 账号，仍共用同一 `data/cookies/cnki_cookies.json` 与同一串行会话，不会出现并发登录互踢。

## 5. 相关文件

- `app/routers/openapi_v1.py`：`API_QUEUE_PRIORITY` 由 `10` 改为 `-1`，注释与 `_queue_position` docstring 同步；
- `tests/test_openapi_v1.py`：优先级断言由 `> 0` 改为 `< 0`；
- `README.md`、`docs/开放接口文档_v1.md`：第 7 节与队列表说明更新，并补充「网页下载不占用检索队列」。
