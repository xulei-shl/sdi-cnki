# 开发变更记录：开放接口接入 JEV 相关性判断

- **日期**: 2026-10-01
- **影响面**: 开放接口默认行为变更（新增相关性判断）；`llm_configs` 表结构变更；新增 `jev` 队列

## 1. 变更摘要

开放接口在 CNKI 检索入库后，新增一步 **JEV（TypeSafe System One）相关性判断**，**默认执行**：

1. 提交作业支持 `relevance` 对象（`enabled` 默认 `true`、`topic` 可选）；
2. 判定引擎从「LLM 提示词」改为 **JEV 的 noul + score 双问题**，折算公式 `relevance_score = round(noul × (档位/4) × 100)/100`；
3. 新增 `scoring` 阶段，作业在评分期间保持 `running`；
4. 状态接口新增 `relevance` 块，结果新增 `relevance_score` / `relevance_level`；
5. 结果接口新增 `sort=relevance` 与 `min_relevance`。

**最重要的设计约束：相关性判断是可选增值环节，失败绝不影响文献交付。** 作业终态恒为 `succeeded`，已检索到的 50~100 条元数据一定能取回；未打分的条目 `relevance_score` 为 `null`（**不是 0**）。

## 2. 为什么是「失败也不阻断」

CNKI 检索成功时，文献已经入库、计数已经可读——这是不可再生的昂贵成果。而相关性判断只是附加价值：它可能因为管理员没配 JEV、TypeSafe 限流、模型返回异常而失败。

若沿用现有 recovery 的「API 作业失败一律回收到 `failed`」口径，一次 JEV 故障会让调用方**既拿不到文献、也拿不到分数**，把一次成功的检索彻底丢弃。因此：

- `jev_worker` 的**所有**分支（含未配置、全部批次失败、意外异常）都收尾到 `completed`；
- `recovery.py` 新增的 `jev` 分支同样落到 `completed` + `relevance_status='failed'`，这是该模块**唯一刻意偏离**统一口径的地方，代码中已注明理由。

失败信息通过 `relevance.state` / `relevance.error` / `counts.relevance.failed` 三处汇总呈现，不影响作业的成功语义。

## 3. 为什么不用 0 兜底，而是 `null`

参考实现（`docs/jev-docs`）在答案字段缺失时按 0 处理。本项目**刻意不这么做**：

- `0` 的语义是「打了低分」——它本就该被 `min_relevance` 过滤掉；
- `null` 的语义是「没有分数」——无法判定，调用方应区别对待。

两者的混淆会让调用方误判文献质量。`skills_api_evaluation_report.md` §2.3 已把「`failed: true` + 占位 0 分」评为 🔴 高危幻觉源。因此本实现：

- 未评分 / 评分失败的条目：`relevance_score = null`，且**不返回任何 `relevance_failed` 布尔标志**（那类内部状态字段同样会诱发幻觉）；
- `min_relevance` 过滤天然排除 `null`，`sort=relevance` 让 `null` 沉底。

## 4. 关键实现决策

### 4.1 复用 `search_completed`，不新增实例状态

作业在检索完成后停在 `search_completed`（`STATE_MAP` 中已映射为对外 `running`），由 `jev_worker` 收尾时才置 `completed`。这样：

- 不改前端 `TaskStatus` 联合类型，不改状态机文档；
- 调用方不会在评分未完成时就看到 `succeeded` 并取到一批 `null`。

`tests/test_jev_scoring.py::test_cnki_worker_enqueues_jev_and_defers_terminal_state` 同时断言内部状态与对外 `_build_status` 的 `running`。

### 4.2 批量口径而非逐篇

50~100 篇逐篇调用需要 50~100 次 JEV 请求。按批（20 篇/批）只需 3~5 次，每篇问一对 `r{i}`/`s{i}`，另加一个批级 `choice` 作显式弃权信号——即参考实现 `jev-reranker.ts` 的精排口径，适配「一次检索的一批文献对同一个定题」这一场景。

### 4.3 独立 `jev_scores` 表，不复用 `llm_analysis_results`

后者的 `parsed_result` 被网页端 `json_extract($.is_target_topic)` 直接过滤，且 `task_result_id` 上有 `unique` 约束。复用会导致两种引擎的结果互相覆盖、污染网页筛选。独立表还让主流程后续迁移时可以与 LLM 结果**并行跑同一批文献做口径对比**再决定切换。

### 4.4 `llm_configs` 加 `config_type` 而非新建表

复用现有加密、CRUD、审计与管理员界面。**必须在 `_load_llm_configs` 过滤 `config_type='llm'`**：JEV 端点不是 chat/completions，`llm_provider` 会拼 `/v1/chat/completions` 从而必然失败。

### 4.5 定题描述两处共用

LLM 提示词尾部注入与 JEV 的 `request` 维度都调用 `app/services/search_topic.py:format_search_conditions`，保证两条判定链路看到**同一份**定题描述，口径不会漂移。

### 4.6 在途配额覆盖评分阶段

`_inflight_job_ids` 原先只数 `cnki` 队列行。cnki 行完成后作业进入评分阶段，若不计入，调用方可无限堆积 JEV 任务。现增查 `jev` 队列行。

## 5. 迁移与兜底中踩到的两个坑（均已修）

### 5.1 alembic 在一次 upgrade 内缓存 Inspector，导致索引被静默跳过

010 迁移首次运行时，`jev_scores` 的两个索引建好了，但 `task_instances.relevance_status` 与 `llm_configs.config_type` 的索引**被静默跳过**：

- 根因：alembic 在一次 `upgrade` 中缓存了 `Inspector`。索引存在性判断复用缓存的 `get_indexes()`，拿到的是加列之前的结果，于是「索引不存在」被误判为「已存在」；
- 危害：表结构缺索引**不会报错**，只在数据量上来后才显现为慢查询——这类缺陷极难在开发期发现；
- 修法：`_create_index_if_missing` 每次重新取 inspector，并把索引创建移出建表分支（`jev_scores` 可能已由 `create_all` 建好，但既有表上新加列的索引仍需补齐）。

已在真实库副本上验证 `upgrade` / 重复 `upgrade`（幂等）/ `downgrade` / `downgrade` 后再 `upgrade`。

### 5.2 超时回收不触发业务对象回收，评分进程崩溃会让作业永久卡住

`reclaim_stale_running` 只把超时的队列行标记为 `failed`，**并不调用 `reconcile_failed_task`**——它只在 worker 执行中抛错的路径上被调用。因此 `jev` 评分期间进程崩溃/重启后：

- 队列行被回收为 `failed`；
- 实例永久停在 `search_completed`（对外映射 `running`），**调用方永远轮询不到终态**。

这与 20260930 的 cnki 事故是同一类缺陷（业务对象悬在中间态）。修法是在 `reclaim_stale_running` 中对回收的行补调 `reconcile_failed_task`，让「执行中抛错」与「进程崩溃」两条失败路径收敛到同一处。该修复对 `cnki` / `llm` 队列同样生效（它们的中间态同样只由异常路径回收）。

`tests/test_jev_scoring.py::test_reclaim_stale_jev_row_also_finalizes_instance` 钉死该不变量：先写测试复现（实例停在 `search_completed`），修复后通过。
