# 开发变更记录：开放接口检索条件回显 + Excel 追加评分列

- **日期**: 2026-10-10
- **影响面**: 状态接口/202 响应新增 `search_conditions` 回显；`GET /metadata-jobs/{job_id}/results?format=excel` 与 `/artifact` 下载行为（请求了相关性判断时）

## 1. 变更摘要

本次包含两项面向 agent 的开放接口增强：

1. **检索条件回显（`search_conditions`）**：状态接口与 202 Accepted 响应返回**完整检索条件**——归一化后的实际检索式 + 主题组/作者/基金 + 年份/更新时间 + 是否核心等，另含 `submitted` 原始入参快照。
2. **Excel 追加 JEV 评分列**：`format=excel` 请求了相关性判断（默认）时，在 CNKI 原始导出文件末尾追加 `相关性评分` / `相关性等级` 两列；`relevance.enabled=false` 时仍返回不含这两列的原始文件。

## 2. 检索条件回显：实现决策

### 2.1 收敛为共享纯函数，杜绝口径漂移

「basic→professional 归一化」与「检索式生成」原本分散在 worker（`cnki_worker.build_professional_search_params`）与浏览器交互器（`ProfessionalCnkiInteractor._build_professional_query`）中。本次抽为独立纯函数模块 `app/services/cnki/query_builder.py`：

- `extract_queries` / `build_professional_search_params` / `build_professional_query` 三者收敛；
- worker 执行、浏览器填表、状态接口回显**全部调用同一函数**，保证「接口回显的检索式 = 实际填入 CNKI 的检索式」；
- `cnki_worker` / `professional_interactor` 改为引用该模块（对外保留同名入口，兼容既有调用）。

### 2.2 回显的是「实际执行形态」，而非原始入参

basic 模式入参会被归一化为 professional（全部关键词合并为 A 组、`query_group_b=[]`），因此 `search_conditions.search_mode` 通常是 `professional`、`query_group_a` 是合并后的关键词。原始入参以 `submitted` 快照保留，二者都可查。

### 2.3 从提交那一刻即可用

`search_conditions` 由 `instance.execution_params.search_params` 快照派生，**排队阶段即可读取**，便于调用方在等待期间核对服务端实际执行的检索式。

## 3. Excel 追加评分列：实现决策

### 3.1 追加到原始文件，而非重建新 Excel

保留 CNKI 原始导出格式与中文表头，只在末尾追加两列。行序对齐依据：原始文件第 1 行为表头，数据行随后，与 DB 中 `task_results` 的入库顺序一一对应（`cnki_worker.process_search_results` 逐条解析入库、重复条目不删除，仅打 `is_duplicate` 标记），故按行对齐即可。

### 3.2 未打分行留空，语义同 JSON 的 null

`relevance_score` / `relevance_level` 为 NULL 的条目（评分失败、重复条目、评分期间）在 Excel 中对应单元格留空，与 JSON 中 `null` 语义一致，不误用 0 兜底。

### 3.3 生成副本而非改写原始文件

每次取结果时按最新分数现算 `_scored_excel_path`，写入 `{原文件名}_scored.xlsx` 副本，不污染 CNKI 原始文件。`results?format=excel`、内联返回与 `/artifact` 下载统一走该副本；源文件不是可解析 xlsx（如测试桩/损坏文件）时回退到原始文件、不报错。
