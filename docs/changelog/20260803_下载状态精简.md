# 开发变更记录：PDF 下载状态精简（跳过 → 失败）

- **日期**: 2026-08-03

## 1. 变更摘要

当前 PDF 下载结果存在 5 种状态值：`pending`（未下载）、`downloading`（下载中）、`completed`（已完成）、`failed`（失败）、`skipped`（跳过）。其中 `skipped` 与 `failed` 在语义上描述的是同一类结果——**下载未成功**，且 `skipped` 的命名容易误导用户以为记录被"跳过"而非"下载失败"。

本次优化将 `skipped` 合并到 `failed`，下载状态精简为 3 个有效值：`pending`、`completed`、`failed`。

## 2. 问题分析

### 2.1 `skipped` 状态的赋值逻辑

在 `app/worker/download_worker.py` 的 `_download_one` 函数中，`skipped` 在以下两种情况下被赋值：

1. **`download_pdf()` 返回 `None`** — 三个来源（zhesheke、wanfang、CNKI）全部未能成功下载有效的 PDF。具体包括：
   - 所有来源返回 `None` 或空字符串
   - 所有来源返回 `"CAPTCHA_TIMEOUT"`（验证码超时）
   - 所有来源抛出异常
   - 所有来源返回的文件名与文章标题不匹配（被删除且不返回路径）

2. **`download_pdf()` 抛出异常** — 被 `_download_one` 的 `except` 块捕获

### 2.2 `failed` 状态在批量下载中是死代码

在 `download_worker.py` 的主循环（第 156-157 行）中，存在 `elif dlr["status"] == "failed": failed += 1` 分支，但 `_download_one` **从不返回 `"failed"`**，因此该分支永远不会被执行。

### 2.3 `failed` 仅存在于单条重试路径

`"failed"` 状态只在使用 `/task-instances/X/results/{result_id}/retry-download` 端点进行单条重试下载时赋值（`task_instances.py` 的 653、662、684、691 行）。在该路径中，`download_pdf()` 返回 `None` 时状态为 `"failed"`。

### 2.4 `downloading` 状态分析

`downloading` 是 `TaskInstance.status`（实例级别状态），在 `download_worker.py:46` 被赋值。**它从未被赋值到 `DownloadResult.download_status`（单条结果级别）**，因此在 `/task-instances/X/results` 接口返回的每条结果数据中不会出现 `downloading` 状态。`downloading` 仅作为 `TaskInstance` 的瞬态中间状态存在。

### 2.5 `wecom_notifier.py` 已忽略 `skipped`

通知服务（`app/services/wecom_notifier.py`）在统计下载结果时只累加 `completed` 和 `failed`，`skipped` 的数据被完全忽略，说明 `skipped` 从未被纳入通知逻辑。

### 2.6 当前状态赋值全景

| `download_status` 值 | 赋值位置 | 语义 |
|----------------------|----------|------|
| `pending` | 默认值（无 DownloadResult 记录时） | 尚未尝试下载 |
| `completed` | `download_worker.py` `_download_one`、`retry_single_download` | 下载成功，PDF 已获取 |
| `skipped` | `download_worker.py` `_download_one` | 下载未成功（与 `failed` 语义重复） |
| `failed` | `retry_single_download` 端点 | 下载未成功 |
| `downloading` | 仅 `TaskInstance.status` | 从未赋值到 `DownloadResult` |

## 3. 升级方案

### 3.1 后端变更

| 文件 | 变更内容 |
|------|----------|
| `app/worker/download_worker.py` | `_download_one` 中两处返回 `"skipped"` 改为 `"failed"`；主循环中移除 `skipped` 计数器，合并到 `failed`；SSE 进度广播和完成消息中移除 `skipped` 字段；日志中 `success + failed + skipped` 改为 `success + failed` |
| `app/routers/task_instances.py` | `get_task_instance` 中 `download_skipped` 计数合并到 `download_failed`；移除 `download_skipped_count` 返回字段；`list_instance_results` 的 `download_status` 过滤器中 `skipped` 分支合并到 `failed` |
| `app/models/download_result.py` | 无需变更（`String(20)` 足够容纳所有值） |

### 3.2 前端变更

| 文件 | 变更内容 |
|------|----------|
| `src/types/index.ts` | `DownloadStatus` 类型移除 `'skipped'` |
| `src/pages/task-result/constants.ts` | `DOWNLOAD_BADGE` 移除 `skipped` 条目；`DOWNLOAD_STATUS_OPTIONS` 移除 `skipped` 选项；`downloadTextColor` 移除 `skipped` 分支 |
| `src/pages/task-result/task-header.tsx` | 进度显示中的 `skipped` 字段移除，UI 改为"成功 X / 失败 Y / 总计 Z" |
| `src/pages/task-result/index.tsx` | `downloadProgress` state 移除 `skipped` |
| `src/pages/task-instance/index.tsx` | 实例详情页的 `download_skipped_count` 显示移除 |

### 3.3 数据库迁移

现有数据库中 `download_results` 表的 `download_status` 字段已有 `skipped` 值。建议在升级时执行数据迁移，将所有 `skipped` 更新为 `failed`：

```sql
UPDATE download_results SET download_status = 'failed' WHERE download_status = 'skipped';
```

## 4. 影响范围

- **导出服务**（`app/services/export_service.py`）：导出 Excel 时 `download_status` 原样输出，`skipped` 变为 `failed`，对消费者来说 `失败` 比 `跳过` 更准确。
- **通知服务**（`app/services/wecom_notifier.py`）：已只统计 `completed` 和 `failed`，`skipped` 被忽略，合并后无影响。
- **PDF 清理服务**（`app/services/pdf_cleanup.py`）：仅通过 `pdf_file_id` 关联清理，不依赖 `download_status` 值，无影响。
- **SSE 实时进度**：前端进度条将不再区分"跳过"计数，所有未成功的下载统一归为"失败"。

## 5. 风险与注意事项

- 前端筛选器中用户将无法再单独筛选"跳过"状态的记录（合并后统一在"失败"中查看）。
- 现有 `skipped` 数据的语义在合并后变为"失败"，需要在产品层面确认用户是否接受此变更（"跳过"暗示可重试，"失败"语义更重）。
- 若未来需要区分"主动跳过"（如用户手动跳过某条）和"下载失败"，需重新引入独立状态，但当前业务场景中不存在此需求。
