# 开发变更记录：开放接口在途限流 + 失败回收缺陷修复

- **日期**: 2026-09-30

## 1. 变更摘要

两件事，前者是新增防护，后者是修复一个真实发生过的缺陷：

1. **在途上限**：`POST /metadata-jobs` 限制同时在途的 API 作业数为 2，超出返回 429 `RATE_LIMITED`（带 `Retry-After`）；
2. **失败回收修复**：API 作业在队列层失败后实例永久卡在 `search_queued`。

## 2. 为什么要加在途上限

前置变更（见 `20260930_开放接口队列优先级调整.md`）把 API 作业的优先级提到了网页检索之前。
好处是 API 不再被网页积压拖延，代价是反过来：**API 侧一旦并发提交，网页检索会全部排在后面**。

`cnki` 队列并发=1、单次检索典型耗时 25~60s，原有代码对提交速率**没有任何限制**：

- 唯一的 `idempotency_key` 是**可选的**，且它是去重语义而非并发闸门；
- 全站没有可复用的限流设施（登录限流的 Rate Limiting 至今仍是 `docs/Milestones.md` 中的待办）；
- 不带 key 时每个 POST 都无条件新建队列行。

因此 10 个并发提交就能让网页检索停滞约 10 分钟；再叠加「agent 超时重试且未带 `idempotency_key`」，
占用会被成倍放大。这是典型的 agent 编排形态，不是理论风险。

### 2.1 为什么按「队列行」而不是按「实例状态」计数

限流最初的想法是统计 `TaskInstance` 中 `source='api'` 且非终态的实例数。但这个口径有个致命问题，
而且**恰好在本次变更前被真实触发过**：

实例 83（`T20260929002`）在队列行早已 `failed` 的情况下，实例永久停在 `search_queued`。
若按实例状态计数，这一个残留就会**永久占掉一个配额**，把一个防护机制变成自我拒绝服务。

因此计数口径改为 **`cnki` 队列中尚未执行的作业行**：

- 队列行才是真正占用串行槽位的对象，且超时会被 `reclaim_stale_running` 回收；
- API 作业的识别依据是 `priority == API_QUEUE_PRIORITY`（网页检索入队用默认值 0）。
  引用同一常量，因此日后调整优先级数值不会让两处口径漂移。

### 2.2 顺序与非副作用

- 在途检查置于**幂等检查之后**：同 `idempotency_key` 重试必须拿回原作业，不能被自家配额拒成 429；
- 置于**分配流水号 / 创建实例之前**：被拒绝的请求不留任何副作用（不建实例、不消耗 `instance_no`）。

## 3. 修复：API 作业队列层失败后永久卡在 search_queued

### 3.1 根因

`app/worker/recovery.py` 的 `reconcile_failed_task` 靠 `row.task_key` 反查业务对象，
cnki 分支直接把 key 当作 `instance_no` 使用。但开放接口在带 `idempotency_key` 时，
入队用的 `task_key` 是 `api_<idempotency_key>`（`openapi_v1.py`）。

于是回收时查找 `instance_no == "api_agent-run-9"` 必然落空，`_reconcile_instance` 静默返回，
实例永久停在 `search_queued` —— 网页端没有该作业（`source=api` 被隔离），
API 调用方则永远轮询不到终态。

实例 83 就是这么产生的：陈旧 `.pyc` 导致 `dequeue` 返回错位列、`params_json` 拿到 task_type 的值，
`run_cnki_search` 在第一个 `json.loads` 就抛错，业务层自己的失败分支根本没机会执行，
只能依赖 worker 的回收兜底 —— 而兜底又因 task_key 不匹配而失效。

### 3.2 修法

1. **优先用 `params_json.instance_id` 定位**，`task_key` 仅作兜底（`_extract_instance_id`，解析失败返回 `None` 而不抛错）；
2. **API 作业统一回收到终态 `failed`**，而不是像网页那样回退到可重试的中间态：
   API 作业没有「重新触发」入口，停在中间态等于让调用方永远轮询。错误消息文案也区分：
   API 为「（作业已失败，请重新提交）」，网页保持「（可重新触发）」。

## 4. 顺带的基础设施改动

- `AppError` 新增可选 `headers`，`app/main.py` 的错误处理器透传，使 429 能带 `Retry-After`；
  其余错误不传该参数，行为不变。
- 新增 `RateLimitedError`（`code="RATE_LIMITED"`, `status_code=429`）。

## 5. 验证

- `tests/test_openapi_v1.py`：11 → 16 项，新增 5 项；全量套件 26 passed（既有 3 failed / 1 error 与本次无关）。
- 新增的回归测试 `test_reconcile_fails_api_instance_despite_prefixed_task_key` 经反向验证：
  临时把 `_extract_instance_id` 退回「只靠 task_key」后该测试确实失败，证明其真实守护该缺陷。
- 新增的 `test_orphaned_instance_does_not_consume_quota` 覆盖「实例卡中间态不占配额」这一口径前提。
