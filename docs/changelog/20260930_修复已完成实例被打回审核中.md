# 开发变更记录：修复「重跑分析把已完成实例打回审核中」

- **日期**: 2026-09-30

## 1. 变更摘要

实例状态改为在审核/下载阶段结束时**由数据派生**，不再由 worker 写死常量。
修复了「对已完成实例重跑分析，终态 `completed` 被覆盖为 `analyzing_completed`」的缺陷。

## 2. 问题

排查 4 条长期停在 `analyzing_completed`（UI 显示「审核中」）的实例时，发现其中
`T20260830002` 是**真缺陷**：7 条审核通过记录全部下载成功，本应 `completed`。

**证据链**

| 时间 | 事件 | 结果 |
|------|------|------|
| 2026-09-01 09:42:50 | 批量下载队列行 `269` 完成 | 7 条通过 / 7 条下载成功 → 应置 `completed` |
| 2026-09-01 09:52:43 | 用户触发「重新分析」（队列行 `292`） | `retry-analysis` 置 `analyzing` |
| 2026-09-01 09:52:47 | 分析完成 | `llm_worker` 写死 `analyzing_completed` → **终态被覆盖** |

`analysis_completed_at` 与队列行完成时间完全吻合，确认覆盖来源。

## 3. 根因：状态是派生值，规则却散落各处

`instance.status` 在 **7 个文件、20 余处**被直接赋值，其中「是否已终态」这条规则
被多个 worker 各自实现，`llm_worker` 的成功分支用了**硬编码常量**：

```python
instance.status = "analyzing_completed"   # 无论此前是否 completed
```

而 `retry-analysis` 端点允许对 `completed` 实例重跑（前端 `canRetryAnalysis`
本就包含 `'completed'`），于是「重跑分析」必然把终态打回中间态。

经枚举全部写状态的位置，**这是唯一会覆盖终态的路径**——其余路径都有前置状态守卫
（如 `complete_task_instance` 要求 `search_completed`、`_revert_download_instances`
只接受 `downloading`/`download_queued`）。

## 4. 修法

新增数据派生的状态判定，作为**唯一**的判定入口：

```python
# app/services/download_progress.py
async def resolve_review_status(db, instance_id) -> str:
    stats = await get_download_progress_stats(db, instance_id)
    if stats["total"] > 0 and stats["success"] >= stats["total"]:
        return "completed"
    return "analyzing_completed"
```

`llm_worker` 的两个收尾分支（正常完成、无可分析记录）改用它，并在流入 `completed`
时补写 `completed_at`；SSE 推送的 `status` 也改为真实状态（前端已支持接收 `completed`）。

判定放在 `download_progress.py` 内，因为它与 `get_download_progress_stats` 共用同一口径
（`total` = 审核通过的非重复记录数），避免两处口径漂移。

### 后续补充

`download_worker` 的同类内联判定当时保持原样，**当天随后已统一**——
它并非只是重复，而是与“重跑时无待下载记录”分支对同一份数据给出不同答案。
详见 `20260930_统一实例终态判定.md`。
