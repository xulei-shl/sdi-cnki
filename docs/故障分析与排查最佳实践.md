## 故障一：邮件测试发送失败

### 现象

通知配置页面点击邮件"测试"按钮，显示`测试发送失败`。

### 排查链路

```text
前端 toast.error('测试发送失败')
  └─ catch 块捕获异常，未展示服务端错误详情
       └─ HTTP 400 from test_email_config()
            └─ RuntimeError("邮件服务未配置，请联系管理员...")
                 └─ send_test_email() 读取 system_configs 为空
                      └─ email_api_url / email_api_key 在表中不存在
```

### 根因

`system_configs` 表在添加邮件功能前已有 7 条记录（webhook、检索超时、并发数等）。种子函数 `_seed_default_configs()` 使用 `COUNT(*) > 0` 判断表非空即跳过，导致后来新增的 `email_api_url` 和 `email_api_key` 两个配置项从未被写入。

### 修复

1. **数据修复**：直接向 SQLite 插入缺失记录。
2. **代码修复**（`app/database.py`）：将 INSERT 改为 `INSERT OR IGNORE`，并移除 `COUNT(*) > 0` 跳过逻辑，使后续新增默认配置时自动写入已有数据库。

### 教训

种子函数设计为"空表写入"而非"按 key 幂等写入"，当已有部署后新增默认配置项时，新配置永远不会被写入，且没有日志或告警。

## 故障二：前端页面无法加载数据

### 现象

Admin 账号下 `/task-instances`、`/prompts` 等页面加载不出数据，显示错误提示，但后端 API 直接调用正常。

### 排查链路

```text
浏览器 → http://10.40.92.18:8848/ 打不开
  └─ ss 确认 8848 端口无监听
       └─ Vite 进程已退出
            └─ 重新启动后短暂可用，随后再次退出

最终可用后：
浏览器 → 页面可打开，但数据加载失败
  └─ 前端 JS 已加载，API 请求通过 Vite proxy 转发到后端
       └─ Vite 进程再次崩溃 → 代理失效 → API 请求 502/连接失败
```

### 根因

Vite 开发服务器进程不稳定，反复崩溃。原因可能是：

- 使用 `nohup` 启动的进程在调用 shell 会话结束后被 SIGHUP 信号杀死（尽管 nohup 理论上应免疫，但在某些 shell 实现或超时机制下仍可能被终止）
- 进程未正确 detach 导致被父进程回收时连带杀死

### 修复

使用 `setsid` 启动 Vite 进程，使其完全脱离当前会话：

```bash
cd /opt/sdi-cnki
setsid npx vite --port 8848 --host 0.0.0.0 </dev/null > data/vite.log 2>&1 &
```

### 教训

- 开发环境用 `nohup` 启动的服务不稳定，进程可能因 shell 会话结束而终止
- 生产环境应使用 `systemd` 管理前端服务，确保自动重启
- 排查"前端页面加载不了数据"时，应先确认前端服务是否存活，再确认 API 代理是否工作，最后确认后端 API 是否正常

## 通用排查原则

### 1. 分层排查法

从前端到后端逐层确认，不要跳过中间层：

```text
[浏览器] → [前端服务/Vite] → [API 代理] → [后端 API] → [数据库]
   ①            ②               ③            ④            ⑤
```

- **①**：浏览器开发者工具 Network 面板，看请求是否发出、状态码、响应体
- **②**：前端服务是否存活（`ss -tlnp | grep 8848`）、能否返回 HTML（`curl http://localhost:8848/`）
- **③**：代理是否正常工作（`curl http://localhost:8848/api/v1/health`）
- **④**：后端 API 是否正常（`curl http://localhost:8456/api/v1/health`）
- **⑤**：数据库是否有数据（`sqlite3 data/cnki_service.db "SELECT ..."`）

### 2. 抓住"钝化"表象背后的事实

前端显示"测试发送失败"时，不要只盯着前端代码。直接调用后端 API 确认功能是否正常：

```bash
# 绕过前端，直接测试后端 API
curl -X POST http://localhost:9000/api/v1/mail/send-sync \
  -H "X-API-Key: 67007" \
  -d '{"to":"...","subject":"test","content":"test"}'
```

如果后端 API 正常，问题在前端或代理；如果后端 API 异常，问题在后端。

### 3. 确认型问题 vs 排查型问题

| 问题类型 | 特征 | 做法 |
|---------|------|------|
| 确认型 | 知道什么变了，只需确认是否生效 | 直接验证，无需追溯 |
| 排查型 | 不知道根因，需要从现象逆推 | 走分层排查链路，逐层缩小范围 |

### 4. 进程稳定性排查

当服务间歇性可用时：

```bash
# 1. 确认进程是否有 PID 文件
cat /var/run/*.pid 2>/dev/null

# 2. 监控进程存活
watch -n 1 'ps aux | grep vite | grep -v grep'

# 3. 查看退出日志
journalctl -u sdi-cnki-frontend --no-pager -n 50

# 4. 检查端口占用
ss -tlnp | grep 8848

# 5. 生产环境使用 systemd，不要用 nohup
```

## 预防性措施清单

### 数据库种子函数

| 措施 | 说明 |
|------|------|
| 使用 `INSERT OR IGNORE` | 避免新增默认配置时遗漏已有部署 |
| 基于 key 幂等，而非基于表空 | `COUNT(*) > 0` 跳过逻辑会遗漏后续新增的配置 |
| 在 AGENTS.md 中备注 | 供 AI agent 在修改种子函数时参考 |

### 前端服务

| 措施 | 说明 |
|------|------|
| systemd 管理 | 生产环境必须用 systemd 管理前端服务，确保崩溃后自动重启 |
| 健康检查 | 监控系统应定期轮询前端端口和 API 代理路径 |
| 日志 | 前端日志应持久化到文件，便于排查崩溃原因 |

### 前端错误处理

| 措施 | 说明 |
|------|------|
| 展示服务端错误详情 | `catch` 块应展示服务端返回的 `detail` 字段，而非仅显示通用提示 |
| 区分可恢复和不可恢复错误 | 网络错误提示重试，业务错误提示具体原因 |

### 排查能力

| 措施 | 说明 |
|------|------|
| 维护 API 直接测试脚本 | 绕过前端直接测试后端 API，快速定位问题层 |
| 维护端口和服务速查表 | 类似部署文档中的端口说明，便于快速确认服务状态 |
| 记录每次故障的排查链路 | 积累经验，未来类似问题可快速定位 |
