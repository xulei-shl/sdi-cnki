# 开放接口文档 v1：CNKI 元数据检索

- **版本**: v1（2026-09-29）
- **基础路径**: `/api/v1/open`
- **用途**: 供 agent / 第三方系统提交 CNKI 检索作业，取回**文献元数据**。只覆盖检索与元数据，**不包含** LLM 分析与 PDF 下载。

配套实现：`app/routers/openapi_v1.py`；变更说明见 `docs/changelog/20260929_开放接口元数据检索.md`。

---

## 1. 接入准备

### 1.1 获取 API Key

API Key 由系统管理员创建（管理员用网页登录态 JWT 调用，不走 API Key）：

```
POST /api/v1/open/keys
Authorization: Bearer <管理员JWT>
{ "name": "my-agent", "expires_in_days": 365 }
```

响应（`api_key` 明文**仅此一次**返回，丢失只能重建）：

```json
{
  "id": 1,
  "name": "my-agent",
  "api_key": "sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "key_prefix": "sk-xxxxxxxxxx",
  "expires_at": "2027-09-29T00:00:00",
  "warning": "API Key 仅此一次返回，请立即保存"
}
```

后续所有作业接口使用该 Key：

```
Authorization: Bearer sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

> **安全提醒**：API Key 等同于系统身份凭证，应保存在调用方的密钥管理系统中（环境变量/密钥库），**不得**写入代码仓库、聊天记录或日志。泄露时立即让管理员执行 `DELETE /keys/{id}` 停用并重建。

### 1.2 服务地址与约定

| 项 | 值 |
|---|---|
| 基础路径 | `/api/v1/open` |
| 请求体 | `application/json`（UTF-8） |
| 响应体 | `application/json`（UTF-8）；文件下载除外 |
| 时间格式 | ISO 8601 本地时间字符串 |
| 串行约束 | 全部作业共享一个串行检索队列，**吞吐上限 = 1 篇/次**，与调用方数量无关 |
| 单作业超时 | 服务端 5400 秒；超时作业会被回收为 `failed` |

## 3. 提交检索作业

### 3.1 请求

```
POST /api/v1/open/metadata-jobs
Authorization: Bearer <API Key>
Content-Type: application/json
```

```json
{
  "search_mode": "basic",
  "queries": ["人工智能"],
  "max_export": 50,
  "idempotency_key": "agent-run-20260929-001"
}
```

### 3.2 请求字段

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `search_mode` | string | 否 | `basic` | `basic`（普通合并检索）或 `professional`（专业检索式） |
| `query` | string | 二选一 | — | 单个检索词（basic 模式）；与 `queries` 至少提供一个 |
| `queries` | string[] | 二选一 | — | 多个检索词（basic 模式），全部合并为一条专业检索式执行 |
| `query_group_a` | string[] | professional 必填 | — | 专业检索 A 组主题词（SU） |
| `query_group_b` | string[] | 否 | — | 专业检索 B 组主题词（TKA），与 A 组为 AND 关系 |
| `au_group` | string[] | 否 | — | 作者限定 |
| `fu_group` | string[] | 否 | — | 基金限定 |
| `year_from` / `year_to` | int | 否 | — | 出版年份范围；与 `date_range` 互斥 |
| `date_range` | string | 否 | — | `week`/`month`/`half-year`/`year`/`ytd`/`last-year` 之一；与年份互斥 |
| `core_only` | bool | 否 | `false` | 仅核心期刊（北大核心/CSCD 等） |
| `synonym_extend` | bool | 否 | `false` | 同义词扩展 |
| `include_no_fulltext` | bool | 否 | `false` | 包含无全文文献 |
| `max_export` | int | 否 | `50` | **只允许 `50` 或 `100`**，其他取值返回 422 |
| `idempotency_key` | string ≤64 | 否 | — | 幂等键：重试时复用同一个值，不会重复排队 |

校验规则（违反返回 400 `VALIDATION_ERROR`）：

- `query` / `queries` / `query_group_a` / `au_group` / `fu_group` 至少一个非空；
- `date_range` 与 `year_from`/`year_to` 不能同时出现；
- `max_export` 只能是 50 或 100（Pydantic 层面直接 422）。

### 3.3 响应（202 Accepted）

```json
{
  "job_id": 12,
  "job_no": "T20260929003",
  "state": "queued",
  "stage": null,
  "stage_message": null,
  "batch": null,
  "queue_position": 2,
  "elapsed_seconds": 0,
  "heartbeat_age_seconds": null,
  "heartbeat_at": null,
  "eta_seconds": null,
  "next_poll_after_ms": 5000,
  "result_ready": false,
  "result_url": null,
  "counts": null,
  "error": null
}
```

| 字段 | 说明 |
|------|------|
| `job_id` | 作业 ID，后续轮询/取结果都用它 |
| `state` | `queued` / `running` / `succeeded` / `failed`（见第 4 节） |
| `queue_position` | 排在前面、尚未执行的检索任务数（**估算值**：只有同优先级的更早 API 作业才排在前面） |
| `next_poll_after_ms` | 服务端建议的下一次轮询间隔，请遵循它 |
| `error` | 仅 `failed` 时非空，为服务端错误摘要 |

## 4. 作业状态与进度语义（防"误判卡死"）

### 4.1 状态机

```
queued ──▶ running ──▶ succeeded
   │           │
   │           └──▶ failed
   └──▶ failed（排队阶段即失败/被取消）
```

终态：`succeeded`、`failed`。进入终态后字段不再变化。

### 4.2 阶段（stage）枚举

| stage | stage_message | 说明 |
|-------|---------------|------|
| `launching` | 正在启动浏览器 | Camoufox 实例启动 |
| `navigating` | 正在打开检索页面 | |
| `authenticating` | 正在校验登录状态 | 可能含验证码等待，最长约 120s |
| `searching` | 正在填写检索条件 | |
| `submitting` | 正在提交检索 | |
| `waiting_results` | 已提交检索，正在等待结果页返回 | 单步最长可达 90s，**属正常耗时** |
| `collecting` | 正在读取检索结果数量 | |
| `exporting` | 正在分批导出元数据 | 附带 `batch: {current, total}` |
| `merging` | 正在合并导出批次 | 上限 100 条时恒为单批次 |
| `parsing` | 正在解析元数据并入库 | |
| `done` | 检索完成 | 终态前最后一个阶段 |

注意：阶段粒度到"浏览器步骤"为止，**不提供百分比进度**——每步时长不可控且导出恒为单批次，百分比只会是假的。

### 4.3 心跳：如何区分"耗时长"与"卡死"

- `heartbeat_at` / `heartbeat_age_seconds`：由**独立心跳任务每 5 秒刷新**，与检索步骤无关；
- **判断规则**：
  - `heartbeat_age_seconds` 在 0~15s 内波动 → 进程活着，只是当前阶段耗时（如 `waiting_results` 卡 90s 属正常）；
  - `heartbeat_age_seconds` 持续增长且明显超过 60s → 服务异常，可判定为卡死，放弃该作业并联系管理员；
  - 服务端另有 5400s 硬超时兜底，超时后作业自动转 `failed`。
- `eta_seconds`：仅 `running` 时可能出现。有历史作业时按最近 10 次均值估算；**无历史时为 `null`，客户端不应假设它一定存在**。

### 4.4 轮询方式

两种方式都支持，agent 推荐长轮询：

**普通轮询**：按 `next_poll_after_ms` 的节奏调 `GET /metadata-jobs/{job_id}`。

**长轮询（推荐）**：

```
GET /api/v1/open/metadata-jobs/{job_id}?wait=25
```

- 服务端最多挂起 25s；期间状态一变立即返回；
- 到点未变则返回当前状态快照（HTTP 200，结构与普通轮询完全一致）；
- 一次 HTTP 调用最多 25s，不会触发客户端请求超时；
- 建议循环：`wait=25` → 读 `state` → 非终态则再发一次。

**判定卡死的完整策略**（给 agent 的伪代码）：

```text
loop:
  s = GET /metadata-jobs/{id}?wait=25
  if s.state in ("succeeded", "failed"): break
  if s.heartbeat_age_seconds is not None and s.heartbeat_age_seconds > 60:
      # 连续两次都超 60s 再放弃，避免网络抖动误判
      consecutive += 1
      if consecutive >= 2: raise "作业疑似卡死，请联系管理员"
  else:
      consecutive = 0
  # elapsed_seconds 超过 5400 也可直接放弃等待服务端兜底
```

## 5. 获取结果

### 5.1 JSON 结果（推荐，agent 默认用这个）

```
GET /api/v1/open/metadata-jobs/{job_id}/results?format=json&limit=50&offset=0
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `format` | `json` | `json` 或 `excel` |
| `limit` | `50` | 1~200 |
| `offset` | `0` | 分页偏移 |
| `inline` | `false` | 仅 `format=excel` 有效，见 5.3 |

前提：作业 `state=succeeded`（或 `counts` 已出现），否则返回 400。

响应：

```json
{
  "job_id": 12,
  "job_no": "T20260929003",
  "count": 50,
  "total": 73,
  "offset": 0,
  "limit": 50,
  "next_offset": 50,
  "records": [
    {
      "id": 901,
      "title": "生成式人工智能对图书馆服务的影响研究",
      "authors": "张三; 李四",
      "organ": "某某大学信息管理学院",
      "source_journal": "图书情报工作",
      "first_duty": "张三",
      "keywords": "生成式AI; 图书馆; 知识服务",
      "abstract": "……",
      "publish_time": "2026-05-20",
      "fund": "国家社会科学基金（23ATQ001）",
      "publish_year": 2026,
      "volume": "",
      "issue": "5",
      "pages": "3-15",
      "clc": "G25",
      "issn": "0252-1167",
      "original_url": "https://kns.cnki.net/...",
      "doi": "10.xxxx/xxxx",
      "reference_format": "张三,李四.生成式人工智能……[J].图书情报工作,2026.",
      "is_duplicate": false
    }
  ]
}
```

分页：`next_offset` 为 `null` 表示已取完；继续带 `offset=next_offset` 请求即可。

### 5.2 条数语义（重要）

- 作业实际导出条数 = `min(CNKI 命中总数, max_export)`，命中不足时**返回条数会少于请求数**，这不是错误；
- `counts.total` = CNKI 命中并导出的总数；`counts.valid` = 去重后的有效条数；`counts.duplicate` = 与历史 API 作业重复的条数；
- **去重说明**：API 作业共享同一内部模板，当前版本跨作业去重开启。与之前任何 API 作业题名+来源重复的记录会被标 `is_duplicate=true`，且计入 `counts.duplicate`。若业务需要每次拿全量原始结果，请以 `records` 全量为准（含重复），或联系管理员调整去重策略；
- `records` 按 `id` 升序稳定排序，分页可重入。

### 5.3 Excel 文件

**方式一：取下载地址（默认）**

```
GET /api/v1/open/metadata-jobs/{job_id}/results?format=excel
```

```json
{
  "job_id": 12,
  "job_no": "T20260929003",
  "filename": "cnki_metadata_T20260929003.xlsx",
  "size_bytes": 48213,
  "content_type": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "download_url": "http://<host>/api/v1/open/metadata-jobs/12/artifact?token=eyJhbGci...",
  "expires_at": "2026-09-29T22:30:00"
}
```

- `download_url` 自带短期签名（默认 **30 分钟**有效），**无需 API Key** 即可下载，可直接交给浏览器/用户；
- 过期后重新调一次本接口即可获得新地址；
- 文件为 CNKI 导出并合并后的原始 xlsx（含中文表头）。

**方式二：内联返回**

```
GET /api/v1/open/metadata-jobs/{job_id}/results?format=excel&inline=true
```

- 直接返回 xlsx 二进制（`Content-Disposition: attachment`）；
- 文件超过 5MB 时返回 413，请改用方式一。

**方式三：直链**

```
GET /api/v1/open/metadata-jobs/{job_id}/artifact?token=<签名>
Authorization: 可省略（有 token 时）
```

不带 `token` 时必须带 API Key。

## 6. 错误处理

所有业务错误返回统一结构（HTTP 状态码 + `code`）：

```json
{ "code": "NOT_FOUND", "message": "MetadataJob not found: 99", "request_id": "a1b2c3d4" }
```

| HTTP | code | 触发场景 | agent 建议动作 |
|------|------|----------|----------------|
| 400 | `VALIDATION_ERROR` | 检索条件非法、结果未产出 | 修正参数或等待终态 |
| 401 | `AUTH_FAILED` | 缺失/错误/过期的 Key 或 token | 停止重试，找管理员换 Key |
| 404 | `NOT_FOUND` | job_id 不存在（或不属于 API 作业） | 确认 job_id |
| 413 | `PAYLOAD_TOO_LARGE` | 内联 Excel 超 5MB | 改用 `download_url` |
| 422 | — | `max_export` 非 50/100 | 改为 50 或 100 |
| 429 | `RATE_LIMITED` | 在途作业数达上限（当前为 2） | **停止提交**，改为轮询错误消息中列出的已有作业；按 `Retry-After` 秒数退避 |
| 500 | `INTERNAL_ERROR` | 服务端异常 | 可重试一次，仍失败则上报 |

**失败作业重试**：`state=failed` 时先读 `error`；重新提交时**务必带新的 `idempotency_key`**（复用旧 key 只会返回已失败的旧作业）。

**在途上限（429 `RATE_LIMITED`）**：同一时间最多允许 2 个 API 作业处于「排队 + 执行」状态，
超出后提交被拒绝，响应带 `Retry-After` 头，错误消息中会列出当前在途的作业号，例如：

```json
{
  "code": "RATE_LIMITED",
  "message": "在途作业已达上限 2 个（#84、#85）。请改为轮询上述已有作业，或等待 30 秒后再提交。",
  "request_id": "a1b2c3d4"
}
```

应据此**改为轮询 `#84`/`#85`，而不是盲目重试提交**。两点保证：

- 判定依据是 **`cnki` 队列中尚未执行的作业行**，而非实例状态——历史遗留的异常实例不会占掉配额；
- 带 `idempotency_key` 的重复提交**优先于**该限制：同 key 重试始终拿回原作业，不会被自己的配额拒绝。

## 7. 与网页用户的关系（调用方须知）

- **互不踢登录**：API 与网页检索走同一队列、同一 CNKI 账号，天然串行，不会互相挤下线或并触发风控；
- **互相排队**：API 作业与网页检索共用同一条串行队列，会互相排队。**API 作业优先级高于网页任务**（`priority=-1` vs `0`）——有 API 作业在排队时它先出队，网页检索任务排在其后；
- **不占用下载队列**：网页的 PDF 下载走独立的 `download` 队列（并发=1），与检索的 `cnki` 队列互不可见，因此网页批量下载耗时多久都不会让 API 检索排队更久；
- **不污染网页**：API 作业不在网页的实例列表、元任务列表、统计数字中出现，也不触发任何企微/邮件通知；
- **配额自律**：入口限制同时在途的 API 作业数（上限 2，超出返回 429 `RATE_LIMITED`）。调用方仍应控制并发（建议同一 Key 同时最多 1 个在途作业），并对 429 按 `Retry-After` 退避、改为轮询已有作业。

## 8. 完整调用示例（curl）

```bash
BASE="http://localhost:8456/api/v1/open"
KEY="sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx"

# 1. 提交作业（专业检索，上限 100 条）
RESP=$(curl -s -X POST "$BASE/metadata-jobs" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "search_mode": "professional",
    "query_group_a": ["阅读推广", "全民阅读"],
    "query_group_b": ["人工智能"],
    "year_from": 2023,
    "max_export": 100,
    "idempotency_key": "run-20260929-01"
  }')
JOB=$(echo "$RESP" | jq -r .job_id)
echo "job: $JOB"

# 2. 长轮询至终态（每次最多挂 25s）
while :; do
  S=$(curl -s "$BASE/metadata-jobs/$JOB?wait=25" -H "Authorization: Bearer $KEY")
  ST=$(echo "$S" | jq -r .state)
  echo "state=$ST stage=$(echo "$S" | jq -r .stage) hb=$(echo "$S" | jq -r .heartbeat_age_seconds)"
  case "$ST" in succeeded|failed) break ;; esac
done

# 3. 取 JSON 结果（翻页）
OFFSET=0
while :; do
  R=$(curl -s "$BASE/metadata-jobs/$JOB/results?format=json&limit=100&offset=$OFFSET" \
    -H "Authorization: Bearer $KEY")
  echo "$R" | jq '.records[] | {title, authors, doi}'
  OFFSET=$(echo "$R" | jq -r '.next_offset // empty')
  [ -z "$OFFSET" ] && break
done

# 4. 需要原始 Excel 时，取签名直链下载
curl -s "$BASE/metadata-jobs/$JOB/results?format=excel" -H "Authorization: Bearer $KEY" \
  | jq -r .download_url | xargs curl -s -o metadata.xlsx
```

## 9. 已知限制与注意事项

1. **吞吐上限**：全局串行队列，一次只能跑一个检索；多调用方只会共享这个队列，不会并行加速。为避免 API 作业把网页检索长时间挤在队列后面，入口限制同时在途的 API 作业数为 2，超出返回 429；
2. **验证码**：CNKI 风控触发人工验证码时，无人值守场景下作业会失败（`error` 中可见），需人工处理后重试；
3. **管理员可见性**：网页隔离作用于列表与统计；管理员若直接访问实例详情接口仍能看到具体作业；
4. **合规**：自动化批量导出元数据受 CNKI 服务条款约束，请控制频率与用途；
5. **不提供**：LLM 相关性分析、PDF 下载、去重范围自定义——这些是网页端能力，本接口刻意不暴露。

## 11. 真实链路验证记录（2026-09-29）

在生产环境实测了完整链路，过程中发现并修复了两个与开放接口无关但被首次真实流量暴露的存量 bug：

1. **检索线程池污染**：`cnki_worker` 原先用默认线程池执行检索，而 PDF 下载
   （`asyncio.to_thread`）也在同一线程池。下载线程中 Camoufox 的 Playwright sync
dispatcher event loop 未随任务结束而退出时，检索任务复用该线程即报
`Playwright Sync API inside the asyncio loop`。修复：检索改用专用单线程
`ThreadPoolExecutor`（`thread_name_prefix="cnki-search"`），与下载线程池物理隔离，
同时天然保证同进程内检索串行。
2. **陈旧 `.pyc` 缓存**：部署目录中 `app/task_queue/__pycache__` 的字节码与源码
mtime 一致但内容陈旧，导致 `dequeue` 返回错位的列（`params_json` 拿到了
task_type 的值），任务立即失败且无明确提示。修复：`python -m compileall -f`
强制重编后重启恢复正常。排查时曾被`mtime 一致`误导，建议部署脚本统一在
发布后执行 `compileall -f`。

修复后实测结果：提交作业（`阅读推广`，50 条）→ 25 秒完成 → `counts` 返回
`total=50, valid=50, duplicate=0`，JSON 分页与签名 Excel 直链下载均正常。
