# 开放接口文档 v1：CNKI 元数据检索

- **版本**: v1（2026-09-29 首版；2026-10-01 增补相关性判断）
- **基础路径**: `/api/v1/open`
- **用途**: 供 agent / 第三方系统提交 CNKI 检索作业，取回**文献元数据**与 **JEV 相关性分**。不包含 PDF 下载。
- **相关性判断**: 默认执行（2026-10-01 起），由 TypeSafe（JEV）而非提示词判定；失败或未配置时**不影响文献交付**。

配套实现：`app/routers/openapi_v1.py`；变更说明见 `docs/changelog/20260929_开放接口元数据检索.md` 与 `docs/changelog/20261001_开放接口JEV相关性判断.md`。

## 1. 接入准备

### 1.1 获取 API Key

API Key 由系统管理员创建（管理员用网页登录态 JWT 调用，不走 API Key）：

```
POST /api/v1/open/keys
Authorization: Bearer <管理员JWT>
{ "name": "my-agent", "expires_in_days": 365 }
```

管理员 JWT 可通过登录接口获取（也可直接在网页端登录后从浏览器取）：

```
POST /api/v1/auth/login
{ "username": "admin", "password": "<管理员密码>" }
# 响应中的 access_token 即为 JWT，有效期 15 分钟
```

> `expires_in_days` 可省略（不设过期），取值范围 1~3650 天；创建接口返回 **201**。

响应（`api_key` 明文**仅此一次**返回，丢失只能重建）：

```json
{
  "id": 1,
  "name": "my-agent",
  "api_key": "sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "key_prefix": "sk-xxxxxxxxxx",
  "expires_at": "2027-09-29T00:00:00",
  "warning": "API Key 仅此一次返回，请立即保存"
}
```

后续所有作业接口使用该 Key：

```
Authorization: Bearer sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

> **安全提醒**：API Key 等同于系统身份凭证，应保存在调用方的密钥管理系统中（环境变量/密钥库），**不得**写入代码仓库、聊天记录或日志。泄露时立即让管理员执行 `DELETE /keys/{id}` 停用并重建。

|------|------|----------|----------|
| `agent-real-test` | 首次真实链路验证（2026-09-29） | 2026-09-29 | 2027-09-29 |
| `agent-integration` | 外部 agent 接入（2026-09-30 创建，使用中） | 2026-09-30 | 2027-09-30 |

### 1.3 服务地址与约定

| 项 | 值 |
|---|---|
| 基础路径 | `/api/v1/open` |
| 请求体 | `application/json`（UTF-8） |
| 响应体 | `application/json`（UTF-8）；文件下载除外 |
| 时间格式 | ISO 8601 本地时间字符串 |
| 串行约束 | 检索阶段全局串行，**吞吐上限 = 1 篇/次**，与调用方数量无关 |
| 单作业超时 | 分段计：检索阶段 5400 秒、评分阶段 1800 秒。检索超时 → 作业 `failed`；**评分超时 → 作业仍 `succeeded`**（见 3.4 失败语义） |

### 1.4 相关性判断的服务端前置条件

相关性判断由服务端调用第三方服务（TypeSafe / JEV）完成，**调用方无法从接口侧配置它**，只能决定是否请求（`relevance.enabled`）。若管理员尚未在「大模型管理」中创建一条**类型为 JEV** 的配置：

- 作业仍正常执行并返回 `succeeded`；
- 文献元数据**照常返回**；
- `relevance.state` 为 `unavailable`，所有 `relevance_score` 为 `null`。

也就是说，**未配置 JEV 不会让接口报错，也不会让调用方拿不到任何数据**，只是没有相关性分。

## 3. 提交检索作业

### 3.1 请求

```
POST /api/v1/open/metadata-jobs
Authorization: Bearer <API Key>
Content-Type: application/json
```

```json
{
  "search_mode": "basic",
  "queries": ["人工智能"],
  "max_export": 50,
  "relevance": { "enabled": true, "topic": null },
  "idempotency_key": "agent-run-20260929-001"
}
```

> 不传 `relevance` 等同于 `{"enabled": true}`——相关性判断默认执行。只想拿元数据、完全不需要分数的调用方，显式传 `{"enabled": false}` 即可完全跳过该阶段（省去 20~60 秒与上游额度）。

### 3.2 请求字段

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `search_mode` | string | 否 | `basic` | `basic`（普通合并检索）或 `professional`（专业检索，按分组参数构造检索式）。**仅 `professional` 走专业分支，未传或传其它值都按 `basic` 处理** |
| `query` | string | 二选一 | — | 单个检索词（basic 模式）；与 `queries` 至少提供一个 |
| `queries` | string[] | 二选一 | — | 多个检索词（basic 模式），全部合并为一条专业检索式执行 |
| `query_group_a` | string[] | professional 条件必填 | — | 专业检索 A 组主题词，同时参与 `SU` 与 `TKA` 两个字段（见 3.3） |
| `query_group_b` | string[] | 否 | — | 专业检索 B 组主题词，与 A 组为 AND 关系，同样同时参与 `SU` 与 `TKA` |
| `au_group` | string[] | 否 | — | 作者限定（`AU`）；A/B 组都为空时可单独使用 |
| `fu_group` | string[] | 否 | — | 基金限定（`FU %`）；A/B 组都为空时可单独使用 |
| `year_from` / `year_to` | int | 否 | — | 出版年份范围；与 `date_range` 互斥 |
| `date_range` | string | 否 | — | `week`/`month`/`half-year`/`year`/`ytd`/`last-year` 之一；与年份互斥 |
| `core_only` | bool | 否 | `false` | 仅核心期刊（北大核心/CSCD 等） |
| `synonym_extend` | bool | 否 | `false` | 同义词扩展 |
| `include_no_fulltext` | bool | 否 | `false` | 包含无全文文献 |
| `max_export` | int | 否 | `50` | **只允许 `50` 或 `100`**，其他取值返回 422 |
| `relevance` | object | 否 | 默认启用 | 相关性判断配置，见 3.4 |
| `idempotency_key` | string ≤64 | 否 | — | 幂等键：重试时复用同一个值，不会重复排队 |

校验规则（违反返回 400 `VALIDATION_ERROR`）：

- `query` / `queries` / `query_group_a` / `au_group` / `fu_group` 至少一个非空；
- `professional` 模式下以「`query_group_a` / `query_group_b` / `au_group` / `fu_group` 至少一组非空」为准；
- `date_range` 与 `year_from`/`year_to` 不能同时出现；
- `max_export` 只能是 50 或 100（Pydantic 层面直接 422）。

### 3.3 检索式构造规则（重要：本接口不接受原始检索式）

**结论先说：接口执行的是 CNKI 专业检索，与网页端「专业检索」面板手工填写检索式等价；但接口不接收检索式文本，只接收分组关键词，检索式由服务端生成。**

#### 3.3.1 执行方式与网页端的对应关系

出队执行时固定切到 CNKI 的「专业检索」Tab，把服务端生成的布尔表达式填入该 Tab 的输入框，再按网页端同样的方式设置年份/勾选项并提交：

| 环节 | API 行为 | 网页端等价操作 |
|------|----------|----------------|
| 检索入口 | 点击专业检索 Tab | 打开高级检索 → 切到「专业检索」 |
| 检索式 | 服务端生成，填入 `textarea.majorSearch` | 手工在专业检索输入框书写 |
| 年份 | 填起始年/结束年，或选相对时间下拉 | 同样的控件 |
| 核心期刊 / 同义词扩展 / 含无全文 | 勾选对应复选框 | 同样的复选框 |
| 检索次数 | **恒为 1 次** | 1 次 |

两种 `search_mode` 最终**都**走这条路径——`basic` 只是把关键词合并成一条专业检索式（原因见 3.3.4）。**本接口不存在「普通检索」执行路径。**

#### 3.3.2 生成规则（逐条对应实现）

设 `A` = `query_group_a`，`B` = `query_group_b`，组内关键词按传入顺序用 ` + ` 连接（单引号包裹）：

| 传入 | 生成的检索式 |
|------|--------------|
| `basic` 的 `query`/`queries` | `SU=('k1' + 'k2' + …) OR TKA=('k1' + 'k2' + …)` |
| `professional` 仅 A（或仅 B） | `SU=('a1' + …) OR TKA=('a1' + …)`；只传 B 时用 B 的组替换 A |
| `professional` A 与 B 都有 | `(SU=('a1' + …) AND SU=('b1' + …)) OR (TKA=('a1' + …) AND TKA=('b1' + …))` |
| 额外传 `au_group` | 在上式整体外围追加 ` AND AU=('作者1' + '作者2' + …)` |
| 额外传 `fu_group` | 在上式整体外围追加 ` AND FU % ('基金1' + '基金2' + …)`（注意是 `%` 不是 `=`） |
| 只有 `au_group` / `fu_group` | `AU=(…)` 或 `FU % (…)`，两者都有时再 AND 相连 |

示例：`"search_mode": "professional"`，A = `["阅读推广", "全民阅读"]`，B = `["人工智能"]`，`au_group` = `["张三"]`，`fu_group` = `["国家社会科学基金"]`，实际填入 CNKI 的检索式为：

```text
(((SU=('阅读推广' + '全民阅读') AND SU=('人工智能')) OR (TKA=('阅读推广' + '全民阅读') AND TKA=('人工智能'))) AND AU=('张三')) AND FU % ('国家社会科学基金')
```

#### 3.3.3 支持与不支持的能力（调用方必读）

**支持**（等价于网页端专业检索的这几类构造）：

- 字段限定符：`SU`（主题）、`TKA`（篇关摘）、`AU`（作者）、`FU`（基金，`%` 运算符）；
- 组内 OR（`+`）、A/B 组间 AND、以及上述固定的 `SU OR TKA` 双字段覆盖。

**不支持**：

- ❌ 传原始检索式文本（如 `TI=('xx') AND KY=('yy')`）——没有这样的参数；
- ❌ 其它字段限定符：`TI`、`KY`、`AB`、`SO`、`FT` 等；
- ❌ `NOT` / `-` 排除、自定义嵌套括号、OR/AND 的其它组合方式；
- ❌ 对生成结果做任何覆盖——`+`、`AND`、括号结构都由服务端固定。

**关键词不会被当作语法解析**：调用方传入的每个关键词一律被单引号包裹，词内的 `'` 转义为 `\'`。因此传 `人工智能') OR SU=('x` 也只会被当成一个普通（无结果的）词面，**不存在检索式注入**；反过来也说明「用参数拼检索式」这条路走不通——需要上述之外的检索式形态，只能改代码或走网页端。

**非关键词条件不进检索式**：`year_from`/`year_to`、`date_range`、`core_only`、`synonym_extend`、`include_no_fulltext` 都是通过页面控件生效，与生成出来的检索式无关。

#### 3.3.4 为什么 basic 也被折成专业检索

历史上 basic 模式是「每个关键词各检索一次再合并」，结果条数会被关键词数量放大（N 个词 → N × `max_export`），`max_export` 形同失效。现改为「合并成一条专业检索式、只检索 1 次」，`max_export` 才是严格的最终入库上限。

### 3.4 相关性判断（JEV）

检索入库后，服务端调用 **TypeSafe（JEV / System One）** 对每篇文献打相关性分，**默认执行**。

| 字段 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `relevance.enabled` | bool | 否 | `true` | 是否执行。`false` 时行为与 2026-09-30 版一致：不排队、不写库，状态里 `relevance.enabled=false`，结果中无 `relevance_*` 字段 |
| `relevance.topic` | string ≤2000 | 否 | `null` | 自然语言定题描述。**留空则由服务端从检索条件自动派生**（主题A/B组、作者、基金、年份、更新时间、核心期刊），与网页端提示词口径一致 |

示例：

```json
{
  "search_mode": "professional",
  "query_group_a": ["阅读推广"],
  "query_group_b": ["人工智能"],
  "max_export": 50,
  "relevance": { "enabled": true, "topic": "人工智能在图书馆阅读推广中的应用" }
}
```

> `topic` 只快照你的原始入参（可以是 `null`），派生在服务端完成，因此后续调整派生规则不影响已提交的作业。

#### 打分口径

不使用提示词。服务端向 JEV 提交「一批候选 + 统一 state」，每篇问一对问题（`noul` 二值门控 + `score` 0–4 五档），再按固定公式折算：

```
relevance_score = round(noul概率 × (档位 / 4) × 100) / 100    # 0~1，保留两位
```

- `relevance_score`：综合相关性分，`0`~`1`；
- `relevance_level`：JEV 原始档位，整数 `0`~`4`（0 完全不相关 / 1 边缘相关 / 2 中度相关 / 3 高度相关 / 4 完全匹配）。

批次按 20 篇切分、批间并发 3，`max_export=100` 时约 5 次上游请求。上游限流（429）、过载（529）、5xx 与网络超时会自动指数退避重试（最多 2 次，优先遵循 `Retry-After`），单次请求超时 30 秒。

#### ⚠️ 失败语义（务必阅读）

**相关性判断是可选增值环节，失败绝不影响文献交付。** 作业终态恒为 `succeeded`，已检索到的元数据一定能取回：

| 情况 | `relevance.state` | 文献是否可取回 | `relevance_score` |
|------|-------------------|---------------|-------------------|
| 正常完成 | `completed` | ✅ | 有值 |
| 部分批次失败 | `partial` | ✅ | 成功批次有值，失败批次为 `null` |
| 全部批次失败 | `failed` | ✅ | 全部 `null` |
| 服务端未配置 JEV | `unavailable` | ✅ | 全部 `null` |

- **`null` 表示「没有分数」，不等于 `0`。** `0` 是「打了低分」，两者语义不同：调用方筛选强相关文献时应使用 `min_relevance`（见 5.1），它会自动排除 `null`；若用 `relevance_score >= 0` 手工判断，会把「没打上分」与「打了 0 分」混为一谈。
- 接口**不返回** `relevance_failed` 之类的布尔标志位——那类内部状态字段容易让大模型误判为「文献质量低劣」或「整体执行失败」。失败信息只在 `relevance.state` / `relevance.error` / `counts.relevance.failed` 三处汇总呈现。
- 与历史条目重复的文献不参与评分（不花上游额度），其 `relevance_score` 为 `null`。

#### 评分期间取结果的行为

`GET /results` 在 `state=running`（含 `scoring` 阶段）时**已经可以调用**，不会返回 400——此时拿到的是**完整元数据 + 全 `null` 的相关性分**。

因此：

- `result_ready=false` 表示「**尚未全部就绪**」（含评分），它才是「可以按相关性做决策」的信号；
- 只关心文献本身的话，评分期间取到的数据同样可用，不必干等；
- 只想拿分数，就等到 `state=succeeded` 再取。

| 字段 | 说明 |
|------|------|

## 4. 作业状态与进度语义（防"误判卡死"）

### 4.1 状态机

```
queued ──▶ running ──▶ succeeded
   │           │
   │           └──▶ failed
   └──▶ failed（排队阶段即失败/被取消）
```

终态：`succeeded`、`failed`。进入终态后字段不再变化。

**与相关性判断的关系**：`scoring` 阶段仍在 `running` 之内；**相关性判断的任何失败（未配置、限流、超时、进程重启）都不会把作业推向 `failed`**，只会让 `relevance.state` 变为 `unavailable` / `failed`。唯一的 `failed` 来源是检索阶段本身失败（验证码、浏览器异常等）。

### 4.2 阶段（stage）枚举

| stage | stage_message | 说明 |
|-------|---------------|------|
| `launching` | 正在启动浏览器 | Camoufox 实例启动 |
| `navigating` | 正在打开检索页面 | |
| `authenticating` | 正在校验登录状态 | 可能含验证码等待，最长约 120s |
| `searching` | 正在填写检索条件 | |
| `submitting` | 正在提交检索 | |
| `waiting_results` | 已提交检索，正在等待结果页返回 | 单步最长可达 90s，**属正常耗时** |
| `collecting` | 正在读取检索结果数量 | |
| `exporting` | 正在分批导出元数据 | 附带 `batch: {current, total}` |
| `merging` | 正在合并导出批次 | 上限 100 条时恒为单批次 |
| `parsing` | 正在解析元数据并入库 | |
| `scoring` | 正在进行相关性评分 | 附带 `batch: {current, total}`，为 JEV 批次进度（20 篇/批，`max_export=100` 时共 5 批） |
| `done` | 检索完成 | 终态前最后一个阶段 |

注意：阶段粒度到"浏览器步骤"为止，**不提供百分比进度**——每步时长不可控且导出恒为单批次，百分比只会是假的。

**开启相关性判断后 `scoring` 是必经阶段**：`state` 在此期间保持 `running`，直到评分收尾才转 `succeeded`。这样调用方不会在分数还没打完时就看到 `succeeded` 并取到一批 `null`。

### 4.3 心跳：如何区分"耗时长"与"卡死"

- `heartbeat_at` / `heartbeat_age_seconds`：由**独立心跳任务每 5 秒刷新**，与检索步骤无关；
- **判断规则**：
  - `heartbeat_age_seconds` 在 0~15s 内波动 → 进程活着，只是当前阶段耗时（如 `waiting_results` 卡 90s 属正常）；
  - `heartbeat_age_seconds` 持续增长且明显超过 60s → 服务异常，可判定为卡死，放弃该作业并联系管理员；
  - 服务端另有分段硬超时兜底：检索阶段 5400s、评分阶段 1800s。检索超时作业转 `failed`；**评分超时作业仍转 `succeeded`**，只是 `relevance.state=failed`、分数为 `null`——文献不会因为评分卡死而丢失。
- `eta_seconds`：仅 `running` 时可能出现。有历史作业时按最近 10 次均值估算；**无历史时为 `null`，客户端不应假设它一定存在**。

### 4.4 轮询方式

两种方式都支持，agent 推荐长轮询：

**普通轮询**：按 `next_poll_after_ms` 的节奏调 `GET /metadata-jobs/{job_id}`。

**长轮询（推荐）**：

```
GET /api/v1/open/metadata-jobs/{job_id}?wait=25
```

- 服务端最多挂起 25s；期间状态一变立即返回；
- 到点未变则返回当前状态快照（HTTP 200，结构与普通轮询完全一致）；
- 一次 HTTP 调用最多 25s，不会触发客户端请求超时；
- 建议循环：`wait=25` → 读 `state` → 非终态则再发一次。

**判定卡死的完整策略**（给 agent 的伪代码）：

```text
loop:
  s = GET /metadata-jobs/{id}?wait=25
  if s.state in ("succeeded", "failed"): break
  if s.heartbeat_age_seconds is not None and s.heartbeat_age_seconds > 60:
      # 连续两次都超 60s 再放弃，避免网络抖动误判
      consecutive += 1
      if consecutive >= 2: raise "作业疑似卡死，请联系管理员"
  else:
      consecutive = 0
  # elapsed_seconds 超过 5400 也可直接放弃等待服务端兜底
```

> 评分类卡死的处置与检索类不同：若卡在 `scoring`，最终服务端仍会给出 `succeeded` + 无分数的结果。调用方可以**提前放弃等待、直接取 `/results`**——元数据此时已完整入库，不会丢。

### 4.5 相关性判断状态（`relevance`）

此块出现在 **`GET /metadata-jobs/{job_id}`（状态接口）**。`GET /results` 不返回该块，只在记录里带 `relevance_score` / `relevance_level`——想确认「有没有分」要查状态接口。

**调用方应显式读取它，而不是假设一定有分。**

```json
"relevance": {
  "enabled": true,
  "state": "completed",
  "total": 73, "scored": 73, "failed": 0,
  "error": null
}
```

| 字段 | 说明 |
|------|------|
| `enabled` | 提交时是否请求了相关性判断。`false` 时 `state` 恒为 `null`，结果中无 `relevance_*` 字段 |
| `state` | `pending`（已排队）/ `running`（评分中）/ `completed`（全部成功）/ `partial`（部分批次失败）/ `failed`（全部失败或超时或进程重启）/ `unavailable`（服务端未配置 JEV） |
| `total` | 实际参与评分的条目数 |
| `scored` | 成功产分的条目数 |
| `failed` | 未产分的条目数（这些条目的 `relevance_score` 为 `null`） |
| `error` | 失败原因，仅 `partial` / `failed` / `unavailable` 时非空 |

**`state` 不为 `completed` 时作业仍是 `succeeded`**，文献照常可取（见 3.4 失败语义）。

### 4.6 counts 中的相关性计数

`counts` 在结果产出后额外带一个 `relevance` 子块：

```json
"counts": {
  "total": 73, "valid": 70, "duplicate": 3,
  "relevance": { "total": 70, "scored": 68, "failed": 2 }
}
```

`counts.relevance.total` 是**实际参与评分的条目数**（重复条目不参与），因此等于 `counts.valid`；若评分尚未开始则为 `0`。未请求相关性判断（`relevance.enabled=false`）时该子块不出现。

## 5. 获取结果

### 5.1 JSON 结果（推荐，agent 默认用这个）

```
GET /api/v1/open/metadata-jobs/{job_id}/results?format=json&limit=50&offset=0&fields=core
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `format` | `json` | `json`、`excel` 或 `json_file`（见 5.3 与 5.4） |
| `fields` | — | **字段裁剪（AI Agent 强烈推荐）**：支持预设视图 `core`（返回篇名、作者、期刊、年份、知网直链、ID 与相关性分共 8 个核心字段），或逗号分隔字段名（如 `title,authors,relevance_score`），别名 `doc_id` 自动映射为 `id`。默认不传时返回全量 21 个字段（19 个学术元数据 + `relevance_score`、`relevance_level`） |
| `sort` | `id` | `id`=按入库顺序（稳定、可重入）；`relevance`=按相关性分**降序**，未打分条目沉底 |
| `min_relevance` | — | `0.0`~`1.0`。只返回分数不低于该值的条目；**`null`（未打分）会被自动排除**。`total` / `next_offset` 按过滤后的集合计算 |
| `limit` | `50` | 1~200 |
| `offset` | `0` | 分页偏移 |
| `inline` | `false` | 仅 `format=excel` 或 `format=json_file` 有效，见 5.3 与 5.4 |

前提：结果已产出（内部状态 `search_completed` 或 `completed`），否则返回 400。

> 由于 `search_completed` 也满足该条件，**评分期间（`state=running`）本接口即可调用**，返回完整元数据 + 全 `null` 的分数。若要分数请等 `state=succeeded`；`result_ready` 为 `false` 即表示评分尚未结束。详见 3.4「评分期间取结果的行为」。

#### 💡 Agent 场景最佳实践：`fields=core` 与 `limit=10`
知网论文的结构化长摘要（`abstract`）长达 300~800 字，全量返回 50~100 篇时体积达 100KB~200KB（消耗 50,000~100,000+ Tokens），易触发 Subprocess/CLI 缓冲区截断崩溃或导致模型上下文溢出。
* **初筛/研报感知**：请求时带上 `fields=core&limit=10`，仅需约 3KB（几百 Tokens），响应极速且安全；
* **全量留存**：使用 5.4 节的 `format=json_file` 或 `format=excel` 获取文件静态直链落地到磁盘/知识库。

响应（`fields=core` 示例）：

```json
{
  "job_id": 12,
  "job_no": "T20260929003",
  "count": 10,
  "total": 73,
  "offset": 0,
  "limit": 10,
  "next_offset": 10,
  "records": [
    {
      "id": 901,
      "title": "生成式人工智能对图书馆服务的影响研究",
      "authors": "张三; 李四",
      "source_journal": "图书情报工作",
      "publish_year": 2026,
      "original_url": "https://kns.cnki.net/...",
      "relevance_score": 0.82,
      "relevance_level": 4
    }
  ]
}
```

默认全量字段（不传 `fields` 时）：
返回 21 个字段——19 个完整学术元数据（`id`, `title`, `authors`, `organ`, `source_journal`, `first_duty`, `keywords`, `abstract`, `publish_time`, `fund`, `publish_year`, `volume`, `issue`, `pages`, `clc`, `issn`, `original_url`, `doi`, `reference_format`）加 `relevance_score`、`relevance_level`。为避免大模型产生“结果存在重复/无效”等幻觉干扰，API 结果不包含系统内部定题状态字段（如 `is_duplicate`），也**不包含相关性评分是否失败的布尔标志**——未打分一律为 `null`。

分页：`next_offset` 为 `null` 表示已取完；继续带 `offset=next_offset` 请求即可。

#### 💡 只要强相关文献

```
GET /api/v1/open/metadata-jobs/12/results?fields=core&sort=relevance&min_relevance=0.7&limit=10
```

先按阈值过滤、再按分数降序取前 10 条——Agent 一次请求即可拿到「最值得读的 10 篇」，无需自己拉全量再排序。未打分条目（`null`）会被 `min_relevance` 自动排除并沉到 `sort=relevance` 的末尾。

### 5.2 条数语义（重要）

- 作业实际导出条数 = `min(CNKI 命中总数, max_export)`，命中不足时**返回条数会少于请求数**，这不是错误；
- `counts.total` = CNKI 命中并导出的总数；`counts.valid` = 去重后的有效条数；`counts.duplicate` = 与历史 API 作业重复的条数；
- 默认不传 `fields` / `sort` / `min_relevance` 时，`records` 输出当前检索导出的全部纯净文献元数据；传入这三个参数则按参数裁剪、过滤、重排；
- 默认按 `id` 升序稳定排序，分页可重入；传 `sort=relevance` 时改为按分数降序、`id` 升序兜底。

## 6. 错误处理

所有业务错误返回统一结构（HTTP 状态码 + `code`）：

```json
{ "code": "NOT_FOUND", "message": "MetadataJob not found: 99", "request_id": "a1b2c3d4" }
```

| HTTP | code | 触发场景 | agent 建议动作 |
|------|------|----------|----------------|
| 400 | `VALIDATION_ERROR` | 检索条件非法、结果未产出 | 修正参数或等待终态 |
| 401 | `AUTH_FAILED` | 缺失/错误/过期的 Key 或 token | 停止重试，找管理员换 Key |
| 404 | `NOT_FOUND` | job_id 不存在（或不属于 API 作业） | 确认 job_id |
| 413 | `PAYLOAD_TOO_LARGE` | 内联 Excel 超 5MB | 改用 `download_url` |
| 422 | — | `max_export` 非 50/100 | 改为 50 或 100 |
| 429 | `RATE_LIMITED` | 在途作业数达上限（当前为 2） | **停止提交**，改为轮询错误消息中列出的已有作业；按 `Retry-After` 秒数退避 |
| 500 | `INTERNAL_ERROR` | 服务端异常 | 可重试一次，仍失败则上报 |

**失败作业重试**：`state=failed` 时先读 `error`；重新提交时**务必带新的 `idempotency_key`**（复用旧 key 只会返回已失败的旧作业）。

> **相关性判断不会产生任何错误码。** 未配置 JEV、上游限流/故障、评分超时、评分进程重启——这些都**不会**返回 4xx/5xx，也不会让作业 `failed`；只体现为 `relevance.state` 与 `null` 分数。调用方**不需要**为相关性做任何错误处理分支。

**在途上限（429 `RATE_LIMITED`）**：同一时间最多允许 2 个 API 作业处于「排队 + 执行」状态，
超出后提交被拒绝，响应带 `Retry-After` 头，错误消息中会列出当前在途的作业号，例如：

```json
{
  "code": "RATE_LIMITED",
  "message": "在途作业已达上限 2 个（#84、#85）。请改为轮询上述已有作业，或等待 30 秒后再提交。",
  "request_id": "a1b2c3d4"
}
```

应据此**改为轮询 `#84`/`#85`，而不是盲目重试提交**。三点保证：

- 判定依据是 **`cnki` 与 `jev` 两个队列中尚未执行的作业行**，而非实例状态——历史遗留的异常实例不会占掉配额；
- **评分阶段同样占用配额**。cnki 行完成后作业进入评分阶段，若不计入，调用方就能无限堆积评分任务；
- 带 `idempotency_key` 的重复提交**优先于**该限制：同 key 重试始终拿回原作业，不会被自己的配额拒绝。

## 7. 与网页用户的关系（调用方须知）

- **互不踢登录**：API 与网页检索走同一队列、同一 CNKI 账号，天然串行，不会互相挤下线或并触发风控；
- **互相排队**：API 作业与网页检索共用同一条串行队列，会互相排队。**API 作业优先级高于网页任务**（`priority=-1` vs `0`）——有 API 作业在排队时它先出队，网页检索任务排在其后；
- **不占用下载队列**：网页的 PDF 下载走独立的 `download` 队列（并发=1），与检索的 `cnki` 队列互不可见，因此网页批量下载耗时多久都不会让 API 检索排队更久；
- **不污染网页**：API 作业不在网页的实例列表、元任务列表、统计数字中出现，也不触发任何企微/邮件通知；
- **不干扰网页相关性分析**：API 作业的 JEV 评分走独立的 `jev` 队列，不占用网页 `llm` 队列的并发（网页 LLM 分析并发=5），两者互不排队；
- **配额自律**：入口限制同时在途的 API 作业数（上限 2，超出返回 429 `RATE_LIMITED`）。调用方仍应控制并发（建议同一 Key 同时最多 1 个在途作业），并对 429 按 `Retry-After` 退避、改为轮询已有作业。

## 8. 完整调用示例（curl）

```bash
BASE="http://localhost:8456/api/v1/open"
KEY="sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx"

# 1. 提交作业（专业检索，上限 100 条）
RESP=$(curl -s -X POST "$BASE/metadata-jobs" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "search_mode": "professional",
    "query_group_a": ["阅读推广", "全民阅读"],
    "query_group_b": ["人工智能"],
    "year_from": 2023,
    "max_export": 100,
    "idempotency_key": "run-20260929-01"
  }')
JOB=$(echo "$RESP" | jq -r .job_id)
echo "job: $JOB"

# 2. 长轮询至终态（每次最多挂 25s）
while :; do
  S=$(curl -s "$BASE/metadata-jobs/$JOB?wait=25" -H "Authorization: Bearer $KEY")
  ST=$(echo "$S" | jq -r .state)
  echo "state=$ST stage=$(echo "$S" | jq -r .stage) hb=$(echo "$S" | jq -r .heartbeat_age_seconds)"
  case "$ST" in succeeded|failed) break ;; esac
done

# 3. 看一眼相关性判断的结果（未打分 / 部分失败都在这里，不要假设一定有分）
curl -s "$BASE/metadata-jobs/$JOB" -H "Authorization: Bearer $KEY" \
  | jq '{state, relevance, counts}'

# 4. 取最相关的 10 篇（轻量视图，约 3KB）
curl -s "$BASE/metadata-jobs/$JOB/results?format=json&fields=core&sort=relevance&min_relevance=0.7&limit=10" \
  -H "Authorization: Bearer $KEY" | jq '.records[] | {title, relevance_score}'

# 5. 全量翻页（含相关性分）
OFFSET=0
while :; do
  R=$(curl -s "$BASE/metadata-jobs/$JOB/results?format=json&limit=100&offset=$OFFSET" \
    -H "Authorization: Bearer $KEY")
  echo "$R" | jq '.records[] | {title, authors, relevance_score}'
  OFFSET=$(echo "$R" | jq -r '.next_offset // empty')
  [ -z "$OFFSET" ] && break
done

# 6. 需要原始 Excel 时，取签名直链下载（不含相关性分）
curl -s "$BASE/metadata-jobs/$JOB/results?format=excel" -H "Authorization: Bearer $KEY" \
  | jq -r .download_url | xargs curl -s -o metadata.xlsx
```

## 9. 已知限制与注意事项

1. **吞吐上限**：全局串行队列，一次只能跑一个检索；多调用方只会共享这个队列，不会并行加速。为避免 API 作业把网页检索长时间挤在队列后面，入口限制同时在途的 API 作业数为 2，超出返回 429；
2. **验证码**：CNKI 风控触发人工验证码时，无人值守场景下作业会失败（`error` 中可见），需人工处理后重试；
3. **管理员可见性**：网页隔离作用于列表与统计；管理员若直接访问实例详情接口仍能看到具体作业；
4. **合规**：自动化批量导出元数据受 CNKI 服务条款约束，请控制频率与用途；
5. **相关性判断依赖服务端配置**：由管理员在「大模型管理」中新建一条**类型为 JEV** 的配置（详见 1.4）。未配置时接口行为不变——作业成功、文献照常返回，只是 `relevance.state=unavailable` 且分数全为 `null`。调用方只能通过 `relevance.enabled` 决定是否请求，无法从接口侧配置上游；
6. **评分耗时**：相关性判断在检索之后串行执行，`max_export=100` 时约 5 次上游请求，典型增加 20~60 秒（未经真实 Key 实测，仅为估算）。超时上限 1800 秒，超时后作业仍为 `succeeded`；
7. **Excel 不含分数**：`format=excel` 返回 CNKI 原始导出文件，无相关性分。需要分数请用 `format=json` 或 `format=json_file`；
8. **不提供**：PDF 下载、去重范围自定义、LLM 提示词式分析（网页端能力，本接口刻意不暴露）；
9. **检索式受限**：只支持按分组关键词构造专业检索式（`SU`/`TKA`/`AU`/`FU`），**不支持直传原始检索式文本**，也不支持 `TI`/`KY`/`NOT` 等其它形态；详见 3.3。

## 11. 真实链路验证记录（2026-09-29）

在生产环境实测了完整链路，过程中发现并修复了两个与开放接口无关但被首次真实流量暴露的存量 bug：

1. **检索线程池污染**：`cnki_worker` 原先用默认线程池执行检索，而 PDF 下载
   （`asyncio.to_thread`）也在同一线程池。下载线程中 Camoufox 的 Playwright sync
dispatcher event loop 未随任务结束而退出时，检索任务复用该线程即报
`Playwright Sync API inside the asyncio loop`。修复：检索改用专用单线程
`ThreadPoolExecutor`（`thread_name_prefix="cnki-search"`），与下载线程池物理隔离，
同时天然保证同进程内检索串行。
2. **陈旧 `.pyc` 缓存**：部署目录中 `app/task_queue/__pycache__` 的字节码与源码
mtime 一致但内容陈旧，导致 `dequeue` 返回错位的列（`params_json` 拿到了
task_type 的值），任务立即失败且无明确提示。修复：`python -m compileall -f`
强制重编后重启恢复正常。排查时曾被`mtime 一致`误导，建议部署脚本统一在
发布后执行 `compileall -f`。

修复后实测结果：提交作业（`阅读推广`，50 条）→ 25 秒完成 → `counts` 返回
`total=50, valid=50, duplicate=0`，JSON 分页与签名 Excel 直链下载均正常。
